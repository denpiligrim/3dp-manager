# Фоновые операции и Журнал

Генерация инбаундов, удаление подписок и нод, удаление relay и установка/удаление перенаправления выполняются через очередь в PostgreSQL. HTTP-запрос возвращает `202` и `jobId`; фронтенд отслеживает `/api/operations/:id` и сохраняет индикатор выполнения до результата. Прямые интеграции с API также должны проверять результат задачи, а не считать `202` завершением операции.

Один обработчик последовательно выполняет задачи в порядке поступления. PostgreSQL advisory lock исключает одновременную работу обработчиков разных экземпляров приложения. Пакетная ротация сохраняет контрольную точку после подписки и уступает очередь другим задачам: удаление не ждёт окончания всего большого пакета. Пока обновляется конкретная подписка, синхронное создание/изменение подписок, нод и relay возвращает `409`, чтобы настройки не менялись посреди генерации. Между подписками блокировка освобождается. Повторный запрос той же незавершённой задачи возвращает её существующий `jobId`.

Пакетная ротация загружает по 10 идентификаторов и обрабатывает одну подписку за раз. Ошибка отдельной подписки записывается в Журнал и не прерывает остальные. Новые инбаунды сначала имеют состояние подготовки: клиентские подписки их не получают до успешного создания всего набора. При ошибке выполняется откат новых инбаундов; неудавшаяся очистка остаётся в БД для следующей ротации. Перед новым созданием незавершённая очистка повторяется: если панель продолжает отклонять удаление, новые инбаунды не добавляются, чтобы не накапливать их на ноде. Рабочие подключения сохраняются.

Запросы изменения на одной панели выполняются последовательно. Создание и удаление имеют до трёх попыток с увеличивающейся задержкой. При потере ответа на создание проверяется уникальный tag на панели; если результат проверить нельзя, повторное создание не отправляется вслепую. После потери ответа на удаление отсутствие инбаунда проверяется через список панели. Ошибки конфигурации не повторяются автоматически.

Очередь сохраняется после перезапуска. Задача, которая уже выполнялась в момент остановки, получает статус «Прервано»: она не запускается заново автоматически, поскольку операция на ноде могла завершиться без сохранения ответа. Проверьте состояние в Журнале и на панели перед повторным запуском.

Раздел «Журнал» содержит очередь, ход генерации, повторные запросы и результаты создания/изменения/удаления подписок, нод и relay. Секреты подключения, настройки клиентов и вывод SSH в него не записываются. Завершённые записи удаляются ежедневно: срок хранения — 30 дней, дополнительно действует предел 50 000 записей.

## Обновление БД

Добавлена миграция `1793300000000-add-operations`: таблица `operation` и поле `inbound.isPending`. В стандартном compose схема обновляется через `DB_SYNCHRONIZE=true`. Если синхронизация отключена, примените миграции с `DB_MIGRATIONS_RUN=true` при обновлении backend. Не запускайте новую версию без обновления схемы.

## Ограничение нагрузки

- `PANEL_MUTATION_INTERVAL_MS`: минимальная пауза между изменениями на панели, по умолчанию 300 мс, допустимый диапазон 100–5000 мс.
- `ROTATION_SUBSCRIPTION_PAUSE_MS`: пауза между подписками, по умолчанию 500 мс, диапазон 100–10000 мс.

При слабых нодах увеличьте паузы. Дополнительный Redis или отдельный контейнер обработчика не требуются. Очередь ограничена 1000 незавершёнными задачами.
